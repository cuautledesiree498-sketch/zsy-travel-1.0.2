# ZSY Travel 首页审查与修改清单

更新时间：2026-04-21 11:35（Asia/Shanghai）

## 文件用途
这份文件用于沉淀 ZSY Travel 首页从“审查问题”到“逐轮修改”的连续上下文，避免对话过长后丢失待办与判断依据。

---

## 一、最初审出来的核心问题（长期有效）

### 1. 首页首屏信息密度过高
- 第一屏文字偏多、偏密
- 用户进入后需要理解的点太多
- 缺少高端旅行品牌首页应有的留白感

### 2. Hero 主标题定位不对
- 早期版本让 `Infinite Travel / 无限旅途` 直接承担 H1
- 问题：品牌名本身不能代替价值表达
- 正确方向：H1 应优先传达“这家网站是做什么、对谁有价值”

### 3. 右侧 trust 卡更像说明器，不像判断辅助块
- 原本更像一段解释服务流程的说明卡
- 问题：第一屏不该过度解释“我们怎么服务你”
- 正确方向：应改成更像旅行者自我判断的辅助块

### 4. Hero 下方 Highlight 区模板味重
- 三列卡片更像常见模板型卖点卡
- 问题：缺少旅行决策入口感
- 正确方向：更像“从哪种旅行想法开始”的入口，而不是平铺功能卖点

### 5. 整体说明味过重
- 首页有较强“服务说明书”气质
- 句子太完整、太解释、太想讲清楚
- 问题：品牌高级感被削弱

### 6. 中文有 AI 味
- 常见表现：
  - “更清楚 / 更容易比较 / 更容易确认”
  - “把模糊需求整理成方案”
  - “为 XX 提供 XX 支持”
- 问题：像 AI 总结，不像真实品牌在说话

### 7. 英文不够原生
- 早期英文更像中文逻辑直译
- 问题：不够像英文旅行品牌 landing page
- 正确方向：英文应优先按 native landing page copy 写，再回看中文，而不是中译英

### 8. 不应一开始全站重写
- 正确策略：先做首页首屏低风险收口
- 不碰 Sanity schema、不大改结构、不加新依赖

### 9. 不应强行引入新动效库
- 改造前已检查 `package.json`
- 当前未见 GSAP / Framer Motion
- 原则：导入前必须先查 stack，不能硬上动效库

## 三、当前新增出来的待修改项（最新）

### 1. emoji / 小图标问题
- 用户指出：`🧭` 这类小图标不合适
- 当前判断：应删除
- 原因：
  - 容易显得模板化、便宜、AI 感强
  - 不符合高端旅行定制站的质感

### 2. 字还是偏多
- 当前首页已比前两版更顺，但文字仍偏多
- 下一步应继续减字，目标是：
  - Hero supporting 再压缩或考虑删除
  - trust 卡 value 再压短
  - Highlight 区说明进一步减弱或删除
  - 三张卡 desc 再缩短

### 3. 首屏仍偏“认真写文案”
- 虽然 AI 味下降，但还不够松弛
- 仍有“工整、稳、清楚，但不够轻”的问题

### 4. 动态背景网页需求（新方向）
用户希望未来实现：
- 鼠标滚轮往下滑动时
- 网页背景随滚动丝滑变化
- 形成更强的沉浸式视觉体验

当前判断：
- 这是正确方向
- 但属于**首页视觉系统升级**，不是第三轮小修
- 需要单独设计方案，不能和“删图标 / 减字”混做

## 四、后续任务分层

### A. 低风险小修（下一轮可直接执行）
只改首页首屏允许区域，目标：
- 删除 emoji / 不合适的小图标
- 继续减字
- 降低首屏密度
- 让页面更轻、更干净

适合继续由：
- 我拆任务
- OpenCode 执行
- 我验收

### B. 动态背景首页升级（后续独立任务）
需要单独做设计与技术方案，不应直接混进小修。

需要提前明确：
1. 用原生方案还是动效库
2. 背景是图片组、视频还是 CMS 管理
3. 只做首页前几屏还是全页
4. 手机端是否降级为静态背景
5. 性能与 SEO 怎么兼顾
6. 与现有 `app/page.tsx` / section 结构如何共存

当前倾向：
- 第一版优先原生实现
- 不急着上 Framer Motion
- 桌面端启用、手机端降级
- 先做首页，不碰全站
